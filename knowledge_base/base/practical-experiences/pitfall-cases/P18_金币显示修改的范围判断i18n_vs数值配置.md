## 现象

用户需求：**扣减金币时数字前面显示负号**，比如显示 "金币 -20" 而非 "金币 20"。

开发者在接到需求后，第一反应是去修改数值配置（JSON）或导出工具（config_tool.py），试图在数据层添加符号处理逻辑。

## 分析

### 职责边界判定

| 层 | 职责 | gold_change 和 cost.gold 的处理 |
|----|------|-------------------------------|
| **数据层**（JSON） | 存储原始数值（含符号） | `"gold_change": -20` ← 本身已带负号 |
| **工具层**（config_tool.py） | 导出/导入数据，不改动数值 | 导出到 Excel 时自然带负号 `-20` |
| **显示层**（UI + i18n） | 格式化展示给用户 | 翻译键决定显示格式 |

### 各层现状

1. **JSON 数据**：`gold_change` 和 `cost.gold` 已经是带符号数值
   ```json
   {"option_id": "A", "gold_change": 50},
   {"option_id": "B", "gold_change": -20}
   ```

2. **config_tool.py**：导出到 Excel 时数值原样保留，`-20` 显示为 `-20`，不需要额外处理

3. **游戏 UI**：使用翻译键 `GOLD_MINUS` 控制显示模板
   ```gdscript
   # 修改前
   label.text = tr("GOLD_MINUS") % absi(gold_change)
   # 翻译键：GOLD_MINUS = "金币 %d"
   # 显示："金币 20"（丢掉了负号信息）

   # 修改后
   label.text = tr("GOLD_MINUS") % absi(gold_change)
   # 翻译键：GOLD_MINUS = "金币 -%d"
   # gold_change = -20 → 显示："金币 -20"
   ```

### 正确做法

只需修改翻译键的格式串：

```csv
# translations.csv（仅需改这一处）

# 修改前
GOLD_MINUS,金币 %d,Gold %d

# 修改后
GOLD_MINUS,金币 -%d,Gold -%d
```

由于代码中已用 `absi(gold_change)` 取绝对值传入，在翻译模板中加入 `-` 前缀即可正确显示 "金币 -20"。

## 职责边界总结

```
┌─────────────────────────────────────────────┐
│  数值符号 ← JSON 数据本身承载               │
│  config_tool 不做额外处理，原样导出          │
├─────────────────────────────────────────────┤
│  显示格式 ← 翻译键（i18n CSV）承载          │
│  %d / %+d / %+.0f 等格式化符控制呈现方式    │
├─────────────────────────────────────────────┤
│  ❌ 不要：将显示格式写入数值配置             │
│  ❌ 不要：将数值计算逻辑放入 i18n            │
└─────────────────────────────────────────────┘
```

## 教训

**修改前先判断改什么——是数据层、显示层还是工具层？**

这个案例中：
- 数据层（JSON）不需要改——数值已经带符号
- 工具层（config_tool.py）不需要改——导出自然带符号
- 显示层（翻译键 CSV）才是正确的修改点

很多开发者在接到需求时的本能反应是"去改数值"或"去改写代码"，但实际上问题可能出在更上游（数据格式）或更下游（显示模板）。花 2 分钟做职责边界判定，可以避免 2 小时的无效修改。
